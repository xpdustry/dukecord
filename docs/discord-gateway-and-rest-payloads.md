# What Discord gateway events and REST endpoints actually deliver

Research date: 2026-09-15. Every claim below is pinned to `discord/discord-api-docs` at commit `52ecc8a`.

Source files, all under `https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/`:
`developers/events/gateway-events.mdx`, `developers/events/gateway.mdx`, `developers/resources/{guild,channel,message,user,voice,emoji}.mdx`, `developers/topics/{permissions,threads,opcodes-and-status-codes}.mdx`, `developers/interactions/{receiving-and-responding,application-commands}.mdx`, `developers/reference.mdx`.

Undocumented fields are explicitly unsupported and may change without notice ([warning](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L17-L19)). Everything below is only what the docs guarantee.

## 1. Gateway event matrix

Discord's own delivery guarantee is at-least-once-or-never: events "never be sent", "sent exactly one time", or "sent up to N times" ([reference L221-L225](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/reference.mdx#L221-L225)). Reducers must be idempotent.

### 1.2 Guilds

| Event | Intent | Payload shape | Injected / extra | Omitted or partial | Cache action |
|---|---|---|---|---|---|
| `GUILD_CREATE` | `GUILDS` | Either a **full guild object plus extra fields**, or an **unavailable guild object** ([L740-L777](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L740-L777)) | `joined_at`, `large`, `unavailable?`, `member_count`, `voice_states`, `members`, `channels`, `threads`, `presences`, `stage_instances`, `guild_scheduled_events`, `soundboard_sounds` | `voice_states` are **partial and lack `guild_id`**. `presences` are **partial presence-update objects**. | `GUILD_DELETE` | `GUILDS` | Unavailable guild object ([L783-L785](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L783-L785)) | — | `id` plus optional `unavailable` | `unavailable == true` → mark guild unavailable, **keep** its data. `unavailable` **absent** → the bot left / was removed; evict the guild and all children |
| `GUILD_EMOJIS_UPDATE` | `GUILD_EXPRESSIONS` | `{guild_id, emojis}` ([L822-L832](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L822-L832)) | `guild_id` | Whole-array snapshot, not a delta | Replace the guild's emoji set wholesale |
| `GUILD_STICKERS_UPDATE` | `GUILD_EXPRESSIONS` | `{guild_id, stickers}` ([L834-L844](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L834-L844)) | `guild_id` | Whole-array snapshot | Replace the guild's sticker set wholesale |

The large-guild rules, stated in [Request Guild Members L196](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L196) and restated as a warning on Guild Create ([L775-L777](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L775-L777)):

1. No `GUILD_PRESENCES` intent, **or** guild over **75,000 members** → only the bot's own member and members currently in voice.
2. Otherwise, guild over `large_threshold` (Identify, 50–250, default 50) → only members who are online, have a role, have a nickname, or are in a voice channel.
3. Otherwise → all members.

`large` is Discord's own boolean for rule 2/3; `member_count` is the authoritative total and is only ever sent on `GUILD_CREATE`.

#### `REQUEST_GUILD_MEMBERS` (opcode 8)

Opcode `8`, send-only ([opcodes L23](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/opcodes-and-status-codes.mdx#L23)). Structure and limits at [L194-L224](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L194-L224):

| Field | Required | Semantics |
|---|---|---|
| `guild_id` | yes | Exactly **one** guild per request |
| `query?` | one of `query` / `user_ids` | Username prefix. `""` means "all members" |
| `limit` | required when `query` is given | Max members matching `query`. `limit: 0` with `query: ""` means unlimited |
| `presences?` | no (default false) | Requires `GUILD_PRESENCES`; silently forced to `false` otherwise |
| `user_ids?` | one of `query` / `user_ids` | Snowflake or array; capped at 100 returned members |
| `nonce?` | no | Max **32 bytes**; an invalid nonce is *ignored* and the replies come back with no nonce at all |

Other hard limits: `GUILD_MEMBERS` intent required for the full-list form `(query="", limit=0)`; a prefix `query` returns at most 100 members; replies arrive as `GUILD_MEMBERS_CHUNK` with **up to 1000 members per chunk**. A rate limit on this opcode is being introduced ([L206-L208](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway-events.mdx#L206-L208)). Gateway-wide budget is 120 send events per 60 s ([gateway L509](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/events/gateway.mdx#L509)).

## 3. Object field semantics

### 3.1 Nullability convention

[reference L207-L217](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/reference.mdx#L207-L217):

| Notation | Meaning | Java mapping |
|---|---|---|
| `field` / `string` | always present, never null | `String` |
| `field?` / `string` | **optional** — the key may be absent | `Optional<String>` |
| `field` / `?string` | **nullable** — key present, value may be `null` | `@Nullable String` |
| `field?` / `?string` | both | needs a tri-state; `Optional<Optional<String>>` or an explicit `Undefined / Null / Value` type |

The distinction is load-bearing for partial-update merges: *absent* means "unchanged", *null* means "cleared". A naive `Optional<T>` that collapses both will erase data on `GUILD_MEMBER_UPDATE` (`nick?: ?string`) and on `PATCH` bodies documented as "optional **and** nullable".

All snowflakes are strings in JSON, up to 64 bits ([L134-L136](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/reference.mdx#L134-L136)); the timestamp is `(id >> 22) + 1420070400000`, which lets you synthesise pagination cursors from an instant: `(ms - 1420070400000) << 22` ([L160-L170](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/reference.mdx#L160-L170)).

### 3.2 User

[Structure L35-L55](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/resources/user.mdx#L35-L55). Non-optional: `id`, `username`, `discriminator`, `global_name` (nullable), `avatar` (nullable). Everything else optional — including `bot`, so "`bot` absent" does not mean "human", it means "not told".

Partial users appear in: `PRESENCE_UPDATE.user` (only `id` guaranteed, **types not validated**), `mentions[]` on messages, `Message.author` when `webhook_id` is set (then `id`/`username`/`avatar` describe the *webhook*, not a user — [message L65](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/resources/message.mdx#L65)), and `emoji.user`.

### 3.3 Guild Member

[Structure L379-L407](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/resources/guild.mdx#L379-L407). `roles`, `joined_at` (nullable), `deaf`, `mute`, `flags` are non-optional on the base object; `user`, `nick`, `avatar`, `banner`, `premium_since`, `pending`, `permissions`, `communication_disabled_until`, `avatar_decoration_data`, `collectibles` are optional.

Documented exceptions, all of which a reducer must encode:

- `user` is **omitted** in `MESSAGE_CREATE.member` and `MESSAGE_UPDATE.member`.
- `permissions` is populated **only inside an interaction object**.
- `pending` is always present in `GUILD_*` events; in non-`GUILD_` events (which only non-pending users can trigger) it is simply absent.
- `joined_at` is `null` for guest-invited members seen via `VOICE_STATE_UPDATE`.
- Interaction `resolved.members` lack `user`, `deaf`, and `mute`.
- Thread members nested in `GUILD_CREATE.threads` omit `id`, `user_id`, `member`.

### 3.5 Role

[Structure L224-L242](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L224-L242). `permissions` is a **string** bit set (v8+, always string, including overwrite `allow`/`deny` — parse with BigInteger). `position` integer, `@everyone` starts at 0 and **shares the guild's id**. `managed` means integration-owned. `color` is deprecated in favour of the `colors` object (`primary_color`, `secondary_color?`, `tertiary_color?`); secondary/tertiary require the `ENHANCED_ROLE_COLORS` guild feature; a role with `colors.primary_color == 0` does not contribute to the computed user-list colour. `tags` ([L245-L256](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L245-L256)) uses a **`null`-means-true** convention: `premium_subscriber`, `available_for_purchase`, `guild_connections` are present-and-`null` when true and absent when false. A JSON binder that maps missing and null to the same value cannot represent these.

### 3.6 Message

[Structure L25-L73](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/resources/message.mdx#L25-L73).

- `author` is user-shaped but is **not a real user when `webhook_id` is set**; it is the webhook's id/username/avatar. Never write it into the user store in that case.
- `member` (gateway-only) is a partial member **without `user`**.
- `mentions` is an array of users, each optionally with a partial `member` (gateway-only).
- `mention_channels` is only ever populated for crossposted messages, and only for publicly visible text channels.
- `message_reference` ([L327-L347](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/resources/message.mdx#L327-L347)) has `type` `DEFAULT 0` → pairs with `referenced_message`, `FORWARD 1` → pairs with `message_snapshots`. `channel_id` is optional when *sending* a reply but always present when *receiving*.
- `referenced_message` only appears for types `19 REPLY`, `21 THREAD_STARTER_MESSAGE`, `23 CONTEXT_MENU_COMMAND`. **Absent means "not fetched, state unknown"; present-and-null means "deleted".** Three-valued.
- `message_snapshots` is a minimal subset and **excludes `author`**.
- `flags` ([L146-L162](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/resources/message.mdx#L146-L162)): `CROSSPOSTED 1<<0`, `IS_CROSSPOST 1<<1`, `SUPPRESS_EMBEDS 1<<2`, `SOURCE_MESSAGE_DELETED 1<<3`, `URGENT 1<<4`, `HAS_THREAD 1<<5`, `EPHEMERAL 1<<6`, `LOADING 1<<7`, `FAILED_TO_MENTION_SOME_ROLES_IN_THREAD 1<<8`, `SUPPRESS_NOTIFICATIONS 1<<12`, `IS_VOICE_MESSAGE 1<<13`, `HAS_SNAPSHOT 1<<14`, `IS_COMPONENTS_V2 1<<15` (**irreversible once set**).
- `components` is gated by `MESSAGE_CONTENT` along with `content`, `embeds`, `attachments` (empty values) and `poll` (omitted).
- `thread` on a message includes a thread-member object.

### 3.7 Guild

[Structure L20-L69](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/resources/guild.mdx#L20-L69). `owner_id` is always present; `owner` and `permissions` are `GET /users/@me/guilds`-only and relative to the requesting user. `roles`, `emojis`, `features` are non-optional; `stickers` is optional. **`member_count`, `joined_at`, `large`, `unavailable`, and all child arrays exist only on `GUILD_CREATE`** ([L16-L18](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/resources/guild.mdx#L16-L18) points at the gateway doc for exactly this reason). The Unavailable Guild object is `{id, unavailable}` and is what `READY.guilds` and `GUILD_DELETE` carry.

### 3.8 Permissions

The canonical bit table is [Bitwise Permission Flags](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L39-L106), with a per-permission "Channel Type" column (`T` text, `V` voice, `S` stage) marking which bits are meaningful as channel overwrites. Values are variable-length integers serialized as strings; use BigInteger, not `long`, as the docs explicitly advise for long-term stability ([L14-L16](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L14-L16)).

Effective channel permissions are computed in the eight-step order at [L123-L132](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L123-L132), with the reference implementation in the Python pseudo-code at [L136-L187](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L136-L187): guild owner → ALL; else OR `@everyone` with every role's `permissions`; `ADMINISTRATOR` → ALL and overwrites are skipped entirely; then `@everyone` overwrite (deny then allow), then the **union** of all role overwrites (all denies accumulated, then all allows accumulated, deny applied before allow), then the member overwrite (deny then allow).

Consequences a cache must support: computing a member's permissions needs the guild (for `owner_id`), every role the member holds **including `@everyone` which is keyed by the guild id**, and the channel's overwrites. Related rules: implicit denies are *not* expressed in the bits — denying `VIEW_CHANNEL` silently voids the rest, denying `SEND_MESSAGES` voids `MENTION_EVERYONE`/`SEND_TTS_MESSAGES`/`ATTACH_FILES`/`EMBED_LINKS`, denying `CONNECT` voids voice permissions ([L189-L197](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L189-L197)). Threads inherit from the parent channel except that `SEND_MESSAGES` is replaced by `SEND_MESSAGES_IN_THREADS` ([L207-L211](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L207-L211)) — so a thread has no overwrites of its own and must be resolved through `parent_id`. Category "inheritance" is actually [Permission Syncing](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L213-L215): a child is synced only while its overwrites are byte-identical to the parent's, and de-syncs permanently on first divergence. Hierarchy rules (kick/ban/nick/role-edit gated on highest role position) are separate from the bit math and apply only to *actions*, not to computed permission values ([L108-L117](https://github.com/discord/discord-api-docs/blob/52ecc8a1908cc3a8dadb55671aef696bb1ed270e/developers/topics/permissions.mdx#L108-L117)).

## Implications for a normalized cache

Concrete reducer rules, each traceable to a row above.

**Identity and merge**

1. `MESSAGE_CREATE.member` / `MESSAGE_UPDATE.member` lack `user`; store as `merge(member, {user: payload.author})`. Do the same for each `mentions[i].member` with `mentions[i]` as the user.
2. If `message.webhook_id` is set, `author` is a webhook, not a user. Skip the user upsert and skip the member upsert (the docs say `member` is absent in that case anyway).
3. `GUILD_MEMBER_UPDATE` is **not** a full member: it has no `flags` and no `permissions`, and `deaf`/`mute`/`nick` are optional. Field-merge over the cached member; never replace. Do upsert its `user` — this event also fires on user-object changes.
4. `PRESENCE_UPDATE.user` guarantees only `id`, and its field *types are not validated*. Parse defensively and merge only well-typed fields; a malformed value must not poison the user store.
5. Distinguish "key absent" from "value null" across the whole model. `nick?: ?string` on `GUILD_MEMBER_UPDATE` means absent = unchanged, `null` = nickname cleared. Role `tags` uses present-and-`null` to mean *true*.

**Guild lifecycle**

6. `GUILD_UPDATE` carries **no** channels, members, threads, voice states or presences: keep those stores as-is. It *does* carry `roles`, `emojis`, `features`, `stickers?` — replace those wholesale, or you will keep deleted roles forever.
7. `GUILD_DELETE` with `unavailable: true` is an outage: mark unavailable, keep the data. `unavailable` absent means the bot was removed: evict the guild and cascade. Availability and absence are different states; `READY.guilds` seeds every guild in the *unavailable* state.
8. `member_count`, `large`, and `joined_at` arrive only on `GUILD_CREATE`. Preserve them across later `GUILD_UPDATE`s. `with_counts` on `GET /guilds/{id}` gives an *approximate* count and is not a substitute.
9. Track member-set completeness per guild, never per cache. Without `GUILD_PRESENCES`, or above 75,000 members, `GUILD_CREATE.members` is just the bot plus voice participants; between those and `large_threshold` it is only online/roled/nicknamed/in-voice members. Call the store "known members".
10. Backfill `guild_id` onto every child object extracted from `GUILD_CREATE` before storing: channels there may omit it and `voice_states` definitively lack it.

**Threads**

11. `THREAD_CREATE` with `newly_created` may arrive before any `THREAD_LIST_SYNC` for that parent, and `THREAD_CREATE` *without* `newly_created` means "you just gained access to an existing thread". Both are upserts; neither implies the parent's thread set is complete.
12. `THREAD_LIST_SYNC` is destructive by design: clear active threads whose `parent_id` is in `channel_ids` (or all guild threads when `channel_ids` is omitted) before inserting, because the array deliberately includes parents with zero threads.
13. `THREAD_DELETE` gives only `{id, guild_id, parent_id, type}`. Any old-value semantics must come from the cache.
14. Losing channel access produces **no** thread delete event at all. Treat thread absence as unknowable and let threads expire rather than trusting a delete-driven lifecycle.
15. `THREAD_MEMBERS_UPDATE.member_count` is approximate and capped at 50; store it as a hint, not a count. Harvest the guild member and presence nested inside `added_members`.

**Channels and messages**

16. `CHANNEL_UPDATE` / `THREAD_UPDATE` are never emitted for `last_message_id` changes. Update it from `MESSAGE_CREATE` (and from `THREAD_CREATE` for forum/media channels).
17. `CHANNEL_PINS_UPDATE` is absent when a pinned message is deleted, so pin state derived from it will drift. It is only safe as a `last_pin_timestamp` write.
18. Channel objects may reference roles and members that no longer exist; overwrite ids are not foreign keys.
19. Check `flags & (1 << 17)` before trusting any channel field other than `id`, `type`, `position`, `parent_id`. An un-obfuscation arrives as a plain `CHANNEL_UPDATE` with full data — which looks like an ordinary rename unless you inspect the flag.
20. `MESSAGE_UPDATE` is documented as a whole message object with `tts` forced false; there is no documented partial subset. Merge anyway, keyed on `id` + `channel_id`, so that either behaviour is safe.
21. `MESSAGE_REACTION_ADD` carries a full `member` but `MESSAGE_REACTION_REMOVE` carries none. Never assume symmetry between add and remove reducers.
22. REST message objects have none of the gateway extras (`guild_id`, `member`, `channel_type`, `mentions[].member`). A message fetched over REST is a weaker record than one received over the socket; mark provenance.

**Intents and non-obvious sources**

23. `GUILD_MEMBER_UPDATE` arrives for the **bot's own member** even without the `GUILD_MEMBERS` intent. A cache with member caching disabled still needs a self-member slot, and permission recomputation must be driven from it.
24. `TYPING_START.member`, `MESSAGE_REACTION_ADD.member`, `VOICE_STATE_UPDATE.member`, `MESSAGE_CREATE.member`, and `THREAD_MEMBERS_UPDATE.added_members[].member` are all member sources that do not require `GUILD_MEMBERS`. For a single-guild bot these are usually enough to avoid the privileged intent entirely.
25. `INTERACTION_CREATE` needs no intent and is the only source of `member.permissions` and of `channel.permissions` / `channel.app_permissions`. It also bypasses channel obfuscation. Store its resolved objects, but tag resolved channels and members as partial so a later full object is not mistaken for a regression.
26. `GUILD_ROLE_DELETE` does not emit follow-up member updates. Strip the role id from every cached member yourself, then invalidate any cached permission computations for that guild.
27. Without `MESSAGE_CONTENT`, `content` / `embeds` / `attachments` / `components` arrive **empty rather than absent**, and `poll` is omitted. An empty string is indistinguishable from a genuinely empty message unless the cache records the intent state.
28. Every reducer must be idempotent and tolerate gaps: Discord states events may be delivered never, once, or N times. `GUILD_MEMBER_ADD` in particular "may also be sent for users who are already members".
29. Process events in shard sequence order, but do not use `RESUMED` as a cache barrier: everything before it was a replay of missed events delivered in order, and dropping that state defeats resuming.
30. REST writes mostly do not return the new state — `PUT`/`DELETE` member roles return `204`, bulk delete returns `204`, join/leave thread return `204`. The cache must be updated from the resulting gateway event, or optimistically and then reconciled; it cannot be updated from the response body.
